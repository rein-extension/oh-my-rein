---
name: rein
description: Turn Rein on or off, check worker status, sync remote work, and manage concurrent coding tasks from one main conversation, delegate to a configured Worker Host, and review results with explicit task and project context.
---

Keep the current conversation as the personal main agent. Discuss and perform small work directly; use native local subagents where they already meet the task's needs. Rein manages longer remote execution through the configured Host.

Use the action the user gave with the Rein skill (in Codex, mention `$rein:rein` and append `on`, `off`, `status`, or `sync`). Apply these actions to the current conversation, regardless of the remote worker adapter.

- **On** or an explicit request to enable Rein (including the legacy Claude command `/rein:rein` without arguments): call `rein_mode` with `enabled: true`. Check its receipt. If it returns disabled, report the reason and stop. If enabled, call `rein_sync` once.
- **Off**: call `rein_mode` with `enabled: false`. Confirm the change, summarizing any ongoing or uncertain executions from the cached `workerStates`. Leave dispatched work and approvals in place. Stop after the receipt.
- **Status**: call `rein_status` with `view: "executions"`, even when mode is off. Show the mode, Host, last complete sync (`sync.lastSyncedAt`), and any later failed or partial attempt. Group executions by task title and show each execution's goal and state. Follow `pagination.nextOffset` if necessary. Describe these as cached observations. Skip activation, sync, dispatch and approval actions during this command.
- **Sync** (`$rein:rein sync` in Codex), or a request to sync or refresh: call `rein_sync` once for the current conversation and preserve its mode. In Pi, if the extension already supplied a freshly synchronized ledger for this turn, use that receipt. Report the sync state and any results, questions, or pending approvals by task name. When the pass is partial or the Host is unavailable, identify incomplete or cached work and return. The user can request another pass.

The default status view returns user-task summaries and a global attention list across all tasks. Follow `pagination.nextOffset` for more tasks; use `view: "attention"` to page through pending actions. Read a user task with `rein_status` and its `id`; read an execution with `view: "executions"` and its `executionId` as `id`. Read full requirements and reports before judgment. Historical user-task definitions can be read with `id` and `version`. New sessions default to mode off. Tools are runtime-bound; never invent a session ID to retrieve another chat's tasks. Project fallback context persists across chats in the same harness instance; task context and control stay with the original chat.

After activation, give a short confirmation in the user's language using the actual tool receipts: mode enabled, current Host name and connectivity, and the Host-reported concurrency limit (not the number of free slots). For example, only after a successful probe and sync: “Rein 已开启 · Host 已连接 · 最多 2 个 worker 并发。可以直接告诉我任务。” If the probe or subsequent sync fails, say mode is enabled but the connection is unavailable or uncertain; never claim readiness from local mode state alone. If the harness cannot load the tools or bind this session, explain that activation did not complete. If connection.maintenance is true, report that the Host is draining and new executions are paused; do not call it ready for new work. Host connectivity does not verify model access; the first bounded remote task does. Do not create a sample task without a user request. On first activation, briefly explain that the user can keep chatting and ask to sync results. New conversations start with mode off; disabling does not cancel running tasks.

Keep the user in this one main conversation. Create an enduring user task with `rein_task_create` when work needs delegation, using a recognizable title, stable `taskKey`, overall goal and completion criteria. Ordinary discussion does not require a task. Reuse the returned `userTaskId` for investigation, implementation and verification executions of that goal. `rein_dispatch` requires this ID and the current `expectedRevision`; each new execution has its own `requestKey`. Delivery retries reuse that request key. Returned `executionId` and `runId` identify one execution; the legacy `taskId` alias in receipts also identifies that execution, not the user task. Route corrections to the named task; briefly clarify ambiguous references instead of guessing. Independent executions may run concurrently, including multiple executions within one task. Coordinate dependencies, shared baselines and overlapping changes before dispatch. Report recognizable task names, not internal IDs.

Dispatch persists the execution and makes one bounded delivery attempt before returning its receipt. Return control to the user after submission. Describe queued, delivered and uncertain states from receipts accurately. Do not keep a turn open with sleep or repeated polling while workers run. On the next ordinary interaction while mode is on, make one sync pass (skip it for off and cached status) and consider global attention alongside the user's new message; keep unrelated discussion conversational. Status is available locally when SSH is down. Sync has a bounded network budget, so pending commands or more events may need another interaction; it is not a background delivery service. Only wait through completion when the user explicitly asks to wait.

Use `rein_task_update` at its current `expectedVersion` to revise the overall goal/completion criteria, record or clear pending decisions in `waitingFor`, or pause/resume/cancel that user task. Resolve decisions before dispatch. Goal or completion-criteria changes advance `revision`; administrative changes only advance `version`. Pause holds new dispatch and undelivered starts. Already delivered workers may finish, and their results stay available. Use cancellation separately when execution must stop, then sync and confirm termination. Resume releases held delivery without restarting completed or canceled executions. Revising a completed task reopens it; an explicit request to repeat the same completed task can use status active, which also starts a new revision. In either case, old accepted executions cannot satisfy the new revision.

When a worker reports `waiting_input`, read its full report (collect first if omitted) and relay its questions in this main conversation. Do not invent the user's answer. Record a lasting task requirement when appropriate, then re-read the current revision. Use `rein_continue` with the previous execution ID, the user's answers by question ID, a task-relevant message, and an explicit updated snapshot/context selection. This resumes the same native worker session and checkout; it creates a new immutable turn and preserves prior reports. Only the latest safely completed turn can continue. Missing native session data fails rather than silently creating a replacement. A previous turn marked `continued` still needs outcome review, but is not an independently acceptable final result. Each turn's patch is cumulative against the original base: apply the latest intended patch to that base, not on top of earlier turn patches. This is between-turn interaction; native permissions use the separate workflow below.

Approval routing is ask (default) or delegate. Change it only at the user’s explicit direction through rein_mode with mode: "ask" or "delegate"; dispatch cannot choose it. Native worker permissions are separate; use the configuration tools below at the user’s explicit direction. New defaults affect only new worker sessions; existing sessions retain their native configuration. Changing routing affects subsequent executions, not existing approval records. Ordinary operations permitted by the configured native sandbox run normally; ask/delegate does not force a read-only baseline. Native requests pause only their operation in `awaiting_approval`. Sync and show pending permissions under the corresponding task with its name, Host, operation and impact. Use `rein_permission_review` with `userTaskId` to open the trusted user UI: one request opens directly; multiple requests return choices, from which select one specific request. Use execution-level review for unassigned legacy work. Keep internal IDs in tool calls, not user instructions. Inspect full details with `rein_permissions` when needed; summaries may be truncated. Never invent a user quote, supply an allow argument, run the terminal review on the user's behalf, or read/sign with the installation's private approval key. Closing the UI or canceling its tool call leaves the request pending; late responses to canceled reviews cannot authorize execution. Activation checks the connected Host and local UI; if unavailable, explain how to reopen the same conversation in a compatible client. Terminal review is a diagnostic fallback. Offline activation leaves capability unverified.

When the user asks to inspect or change worker access, call `rein_worker_permissions` on the bound connection. Match its Host, project and adapter to the request; a targetId is an identity check, not a way to select a different connection. For an explicit configuration change, use `rein_worker_permissions_set` with that targetId/revision, a stable requestKey, only the requested fields in changes, and a reason summarizing the user's direction. Omitted fields remain unchanged; tools replaces the list. Report before/after settings and scope: all new workers on this Host/project/adapter across conversations, with existing/queued/resumed sessions unchanged. A one-task restriction cannot be implemented by silently changing these shared defaults. Clarify an ambiguous target or requested access; do not broaden defaults merely to unblock a denied operation. Configuration tools do not change ask/delegate or enable mode. Unknown delivery needs a query or an exact retry with the same input/key; it is not proof of failure. A stale revision requires re-reading and reassessing. A recovered change receipt can be historical: report the separately returned current settings, not the old receipt as current. No shell tool or terminal command is needed. If the Host lacks this API, explain the runtime upgrade requirement.

Default `ask` permits no main-agent approval or denial. In `delegate`, inspect the full native command, file or tool request and use `rein_permission_decide` for a reasoned allow or deny based on task authorization. New requests use policy version 2; unversioned delegated requests require user review for an allow, without rewriting their original policy or hash. Rein adds no command or path classifier. Native command acceptance may escape the sandbox; examine that scope. If authorization is unclear, use `rein_permission_review` to ask the user. A declined request is delivered to the paused native operation; do not retry it under another spelling. Decisions and native operation results are separate: acknowledgment does not prove success. An `unknown` result requires inspection, never automatic replay. Until `rein_effects_review` records actual inspection evidence, the runtime holds new dispatch, queued starts and further allows in the same task; unrelated tasks, denial and cancellation remain available. Do not create a new task key to bypass this guard. Already running operations are not retroactively stopped. Stopping an execution or discarding its knowledge review does not establish whether an approved operation had effects; preserve the inspection reminder. Requests marked `unsupported` are adapter limitations with no grant, not user denials. Explain the recorded reason and use an authorized supported alternative; do not offer an allow button for them. An outstanding native approval occupies a Host slot and expires after 30 minutes. Other tasks can use remaining slots. Sync on the next interaction; automatic wake is unverified. Rein does not provide read-only/full-access routing modes. Codex uses native sandbox/approval settings; Claude uses its native permission mode and tools; Pi uses native tools. Claude manual/acceptEdits forwards native permission requests; operations already permitted by Claude do not ask again. Pi toolApproval=all gates every enabled tool, including reads, using an isolated worker extension; never or an omitted legacy setting does not. Pi project trust (--no-approve) is separate from execution approvals. New setup defaults are Claude manual and Pi all with read/search tools. Read the recorded native settings; selecting delegate alone does not activate a disabled approval channel. A decision resumes the pending operation in the same process; do not call rein_continue to answer an execution-time approval. Ordinary requirement questions still use `rein_continue`. Legacy `waiting_permission` reports cannot authorize execution: explain the limitation and arrange a new native worker after reviewing the previous outcome. Changing native worker defaults requires explicit user direction and affects new worker sessions only.

Personal long-term memory belongs to the harness. Respect its native memory settings and do not edit generated memory files or duplicate the personal store in Rein. Native background recall is not a verified immediate writeback receipt. The current adapter reports native writeback as unverified and uses Rein SQLite as the explicit fallback for project agreements and reviewed discoveries. Never claim a Rein record was written to native memory, or that a chat will necessarily become a memory.

Use `rein_context_record` for explicit requirements with a relevant quote and stable request key. Set `appliesTo: {type: "task", taskKey: "..."}` for task-specific goals, decisions and constraints. Use `{type: "project"}` only when the user expressed a reusable project agreement or project-specific preference. Global personal preferences belong to native memory. Do not record secrets or infer preferences from worker output. This is a main-agent record, not independently authenticated transcript evidence. Records default to local-only; mark shareable only when appropriate and authorized.

Task goals, constraints and decisions default to `requiredForTask: true`; preferences and project notes default to optional. Use `requiredForTask: false` for optional background, never to bypass a real requirement. Adding, changing or retiring a required entry also advances its parent task's version and requirement revision in the same transaction, and reopens a completed task. Re-read the task after these mutations. Dispatch requires explicit selection of every active required entry; if one must remain private, keep that work local or agree on a suitable delegated scope instead of exposing it to unblock dispatch.

For a correction, use `rein_context_list` with the taskKey to locate relevant entries, then read the chosen contextId to confirm full content and scope. Update it at the current version with the new quote. Its scope cannot be moved by an update. A correction to one task must not rewrite another task's requirements or a project-wide agreement. Retirement retains history and old snapshots; it is not erasure. Version conflicts require re-reading. Never change a user preference based solely on a worker observation.

Before dispatch, establish the task's request, constraints, acceptance criteria and exact clean Git base commit available on the Host. `originalRequest` is a task-relevant excerpt, not a full transcript. Exclude local-only preferences from every task field. Select relevant shareable `contextIds` and reviewed `knowledgeIds` explicitly; both default to empty. Read discoveries through `rein_status` with `view: "knowledge"`, then `id` for full content. Context and fact lists are previews; inspect truncated entries before selecting. Reconcile conflicting requirements and invalidate obsolete worker facts. MCP dispatch persists intent and attempts bounded delivery; sync later retries pending commands and retrieves new results. The legacy CLI dispatch only queues intent. Dirty tree transfer, active-run steering and automatic merging are not implemented.

Update the user task when a correction changes its overall goal or completion criteria; update the specific context record when a stored requirement changes. Re-read versions between these operations because required context mutations also revise the task. Corrections preserve old task definitions and execution snapshots. Rein pauses further delivery of stale starts and blocks acceptance of stale results, but does not update or cancel running workers. A previous start may already have reached the Host. Inspect and, when needed, cancel and confirm termination before dispatching replacement work. The pending-action brief helps identify these cases; it is not a substitute for judging the result.

On relevant user interactions, sync and handle questions, failed work and ready reports. A disconnect leaves execution uncertain; do not dispatch a replacement writing task. For stopping only one execution, call `rein_cancel` with its `executionId` then sync; distinguish cancellation requested from confirmed. Disabling mode does not cancel existing work.

An unknown execution still occupies a Host slot. Explain the need to inspect processes, workspace and external effects before an operator uses `rein host resolve --task RUN_ID --confirm-stopped --reason ...` with the connection config. Do not infer that this confirmation is authorized merely because a PID disappeared, and do not mark the work successful. Recovery records cancellation and preserves history; sync before considering a replacement execution. A draining Host continues existing work but rejects new starts; do not repeatedly retry dispatch or automatically resume maintenance that the operator requested.

For a ready result, read the full execution via `rein_status` with `view: "executions"` and its ID, collect its artifacts using `executionId`, and inspect the report and patch. Large reports may show `reportOmitted: true` until collection; collect before judging unresolved requirements or discoveries. Verify every criterion before acceptance, with exactly one evidence item per criterion in order. Worker claims alone are not proof. Collecting files does not apply changes to the user's checkout. Report validation still outstanding. Accepting an execution never completes the user task. After all relevant executions are settled and their outcomes reviewed, use `rein_task_complete` with the current task version, selected accepted `executionIds` from its current revision, and exactly one evidence item per overall completion criterion. This records the main agent’s assessment; it does not prove semantic correctness or merge changes.

Review each terminal outcome with `rein_review` and its `executionId` independently of acceptance. Retain relevant discoveries with source and scope, or discard them. Retention records your review, not validation: worker claims remain separately visible as `workerClaimedVerified`. Supply `verificationEvidence` only for checks you actually performed, identifying the command or inspected artifact and result. This records `main-reported` validation, not independently authenticated proof; without it, knowledge remains unverified. Legacy worker-only verification flags are treated as unverified. This prototype retains one reviewed discovery per outcome; combine related content only when the selected source supports it. Worker observations do not establish personal preferences or authorization.

For each unknown operation, first confirm execution stopped and sync; an unknown execution needs Host recovery first. Inspect its workspace and external effects before retrying. Then call `rein_effects_review` with that execution and request ID, actual inspection evidence, and `no-effects` or `effects-addressed`. Do not close unresolved effects or fabricate evidence. This stores a main-reported assessment locally while preserving the original Host approval. It closes the inspection reminder and completion blocker for that request; it does not authorize an operation or replace knowledge review. Read the full execution view for the retained evidence. Unknown effects must be reviewed before completing the parent task.

A cancellation receipt is not the final execution/approval snapshot. When attention includes `sync_execution_final_state`, sync again and wait for final approval cleanup before reviewing effects or completing the parent task. A Host-confirmed never-started execution has no worker outcome to review.

Native worker history retains earlier knowledge and context even when omitted from a new turn. For ordinary user-context corrections, explicitly select the current entry version in the next turn: that version supersedes its earlier reference while old snapshots remain immutable. Omission inherits the latest selected version; it cannot bypass a correction. Retired context requires a fresh worker session. `rein_invalidate` blocks dependent continuations, pending delivery, acceptance and task completion across that history. Use a fresh worker session with corrected knowledge and validate its result. Revoking sharing of a previously selected context entry likewise blocks reuse of its native session, including an already queued continuation. These checks do not erase remote history or retract a start already in flight: inspect and cancel delivered work when needed. Missing local ancestry also requires a fresh session after resolving uncertain work; never recreate history by guessing.

A confirmed Host start rejection can be reviewed with `rein_review` and `decision: "discard"` after inspecting its rejection record. It has no worker run, artifacts or discoveries to retain. This settles the failed attempt's review so it does not block completion after a replacement succeeds. A lost receipt or uncertain delivery requires synchronization and reconciliation; never treat a missing run as proof that nothing started.


The persisted inbox is reliable only to the extent shown by tool receipts. Automatic wake is unverified; do not promise unattended main-agent processing after this chat closes. End the turn when nothing needs judgment rather than repeatedly polling.

Sync reconciles tracked executions with the Host when supported. A Host database identity change blocks delivery; inspect the original Host and pending work before reconnecting or replacing a ledger. Report visible `inboxErrors` instead of describing an incomplete sync as successful.
